验证一个新功能时，本仓库积累出的一套方法。核心不是「跑测试看绿」，而是**先怀疑测试自己会骗人**。

## 三条铁律

1. **先确认后端行为，再动手做前端。** 删除功能那次，先用独立探针实测 `dry_run` 语义，才发现后端早已完整、只缺前端——避免了重写后端。做导出前也应如此。
2. **变异测试证明脚本不是空转。** 每个新功能都要做「该红的红、不该红的不红」：把实现改坏，看断言是否变红；还原，看是否回绿。只跑绿不跑红，等于不知道测试在不在测东西。变异还原见 toolchain 第 1 条。
3. **产品代码不要为了测试好写而改。** 遇到断言过不去，先分清是「产品错了」还是「断言错了」。删除功能那次，实现方想删掉一处正确渲染来让测试通过，被拦住——该改的是断言。

## 判定「测试失败」时先问：是噪音还是信号

- 失败**恰好差 1**且能追溯到某条新数据 → 噪音（硬编码计数）。
- 失败**间歇性**（同代码一次绿一次红）→ 往往是假阳性，比稳定假红更危险，别当 flaky 放过。
- 失败**连锁**从一个点起 → 该点是根因。
- 失败和**本次改动无关**的模块 → 查该模块有无未提交改动，没有就是既有债。

## 并行协作时

- 关键断言、变异测试、还原协议**都要独立复验**，不全信队友报告。
- 读队友正在写的文件会读到半成品（toolchain 第 7 条）。
- 写入范围预先约定并声明，收尾核对 `git status` 只含约定文件。

## 验证脚本的写法约定

- 依赖前置条件的断言要有**第三态「未测到」**：若竞态压根没发生，不判绿（那是把没测伪装成测过）也不判红（不该罚实现），老实报未测到。
- 契约元素（`data-testid`）**只用 testid 不依赖文案**，文案要 i18n。
- 涉及真库的测试**复制一份真库**再跑，绝不污染真库；被试数据用可识别前缀，收尾清理。
- 假阳性判据的修法：限定容器 + 剔除已知会含该文本的节点，或改用结构判据（toolchain 第 3 条）。

## 退出判据

退出码 0 是硬指标。曾出现过 **36/36 全绿却 exit 1**（汇总行引用了块外变量抛 `ReferenceError`）——汇总行也要能跑通，别只看断言计数。
