# 扫描版 PDF 视觉转录：两段式流水线、批量实测与大纲产出

教材扫描件（无可用文本层）进知识库的前置环节。权威源 `packages/core/src/ingest/vision-ocr.ts`、`packages/core/src/ingest/vision-clean.ts`、`scripts/vision-clean.ts`。

## 为什么有些 PDF 必须走视觉

pdfjs 对 **JPEG2000 编码的页面图**直接崩：`JpxError: OpenJPEG failed to initialize`。特征很迷惑——用 pymupdf 查，371 页**每一页都有文本**，看着像"有文本层"，但 pdfjs 一读就抛错。

**判据**：pymupdf 能读、pdfjs 报 `JpxError` → 这是扫描件（页面是整张 JPEG2000 图）。必须走 MuPDF 渲染 + 视觉模型转录，别把 `JpxError` 当解析器 bug 去修。

## 两段式：转录与清洗分开

- `vision-ocr.ts`：单页转录。`DEFAULT_VISION_TIMEOUT_MS`（默认 600_000，可用 `AKG_VISION_TIMEOUT_MS` 覆盖）、`AKG_VISION_CONCURRENCY`（默认 2）。
- `vision-clean.ts`：清洗成带标题结构的 Markdown，是书籍入库的**主路径**。`CLEAN_VERSION` 参与缓存键。

**为什么分开**：转录只负责"把这页的字忠实抄下来"，清洗负责"判断哪些行是标题"。两件事的出错原因完全不同——转录错是看不清，清洗错是判断错。混在一次调用里，判断错会连带污染文字。

## 缓存与失败容忍

- 缓存 `.cache/vision-clean/<文件sha256前16位>/p0016.json`，键含 `CLEAN_VERSION` + model + dpi + file。**改 prompt 必须 bump `CLEAN_VERSION`**，否则读到旧产物。
- **单页失败不拖垮整份**：失败页记进 `failedPages`，其余页照常落缓存。"371 页跑一半炸掉重来"是不可接受的。

## 视觉模型选型：GLM-4.1V-Thinking-Flash 单页快 5 倍，但并发额度按 key 卡

实测日期 2026-11-20，操作系统 371 页扫描书。两个候选：

| 维度 | nvidia `z-ai/glm-5.3-flash` | 智谱 `glm-4.1v-thinking-flash` |
|---|---|---|
| 单页延迟 | ~120s | **~20–25s** |
| 并发额度 | 2（再多只是排队，无收益） | **每 key 1 个** |
| `max_tokens` 上限 | 较大 | **16384 硬顶** |
| 多图合批 | 2 图最优（3 图起 504） | **会丢内容，别合批** |
| 限流失败代价 | 504 要拖满 304s | 429 在 **1 秒内**返回 |

**结论：GLM 的单页速度优势是决定性的**（全书 358 页 2 小时 vs 12 小时）。虽然它并发额度只有 1/key，但单页够快，串行也能赢；而且 429 秒回，重试几乎免费。

**别被「官方说 5 并发」误导**：文档写的是权益等级对应值，`glm-4.1v-thinking-flash` 在免费层标称 5 并发，但**这个 key 实测就是 1**。以实测为准：第 2 个请求 1 秒内返回 429 / 错误码 1302「您的账户已达到速率限制」，响应头里没有任何 `retry-after` / `x-ratelimit-*` 字段。

官方限流口径见 [速率限制](https://docs.bigmodel.cn/cn/api/rate-limit)：限制维度是「**同一时刻正在处理中的请求数**」，不是「每分钟多少次」。已验证：连发 3 个极小请求（间隔 0s）全部成功，0 次 429——所以不是 RPM 限制。

## 多 key 轮转：N 个 key = N 并发（唯一有效的加速手段）

既然额度按 key 计，**调 `concurrency` 参数毫无意义**（服务端按 key 卡，不按进程卡）。多申请 key 是唯一的加速方式。

`packages/core/src/llm/key-pool.ts` 的 `createKeyPool(keys)`：

- **取空闲 key，不轮询**。简单 round-robin 在多 worker 下会撞车（key 数不整除 worker 数时，两个 worker 可能同时被分到同一个 key）。这里全忙就排队，调用方不用关心 key 数量。
- **`release` 必须在 `finally` 里**。任务抛错不归还，池子会越跑越少直到彻底卡死——这条有专门的测试（31-15）。
- **并发数由 key 数决定**：`conc = keyCount > 1 ? keyCount : (opts.concurrency ?? 2)`。开得比 key 多只会排在池里等，开得比 key 少则浪费额度。

key 的发现方式（`collectProviderKeys(provider)`）：`ZHIPU_API_KEY`、`ZHIPU_API_KEY2`、`ZHIPU_API_KEY3`…（第一个不带后缀），也支持逗号分隔塞在一个变量里。

实测：2 个 key 让 6 页从 123s 降到 73s（**1.69×**，未到 2× 是因为图片渲染和缓存写入也占时间）。3 个 key 补跑 13 页用 204s。

## 合批在 GLM 上不可用：会静默丢内容

nvidia 上实测过「2 图最优、3 图必崩」，但**换到 GLM 后合批是另一种坏法**：

- 2 图时覆盖率从 100% 掉到 **61%**（最差一次），页标记齐全、`finish=stop`、HTTP 200，**只有对比原文才发现少了一整段**
- 3 图 0/4 成功

**这种「标记齐全但内容缺失」比直接失败危险得多**，因为它不报错。

另一个必须在代码里处理的问题：批量预算原本是 `maxTokens × 页数`，2 页刚好 16384 擦边，**3 页必然 400**。智谱报错原文 `max_tokens参数非法：限制数值范围[1,16384]`。表现出来只是日志里一行 `zhipu 400`，然后静默回退单页，极难定位。

现在两处都改了：预算按 provider 封顶，且**页数超出预算能装下的量就直接走单页**，不发注定失败的请求。

## 整批失败 → 逐页回退

多页合并只为一件事：省请求。合批后失败有两种——页面内容本身有问题（重跑也失败），或这一批拼在一起超了服务端能力（单页各自都能成）。

所以**整批失败不能标记这批全失败**，要逐页重试。实测 `122+123` 遇 504 回退单页后 122 成功。直接记失败会让 1 次 504 废掉 2 页。

## 提取产出两份：完整正文 + 大纲目录

## 提取产出两份：完整正文 + 大纲目录

一次提取同时产出两个视图，落两份文件：`xxx.clean.md`（正文，逐页带 `<!-- page N -->`）和 `xxx.outline.md`（大纲，带页码）。

**不是两次调用**，是同一份结果的两个投影。这样不会出现「目录说有这节、正文里找不到」的错位。

`extractOutlineEntries(markdown, page)` 从每页正文里抽条目。只认三类**真实编号**：

- `\d+(\.\d+)+` —— `2.1` / `2.3.5`
- `第N章`
- `一、单项选择题`（题组标题，要求后面有 ≥2 字标题文字）

**单个数字 + 顿号/句点（`2．` / `1.`）一律当枚举，不进大纲。** 这是实测踩出来的：转录产物里有 `### 2．读者-写者问题`、`#### 1．生产者-消费者问题`——「1. 2. 3.」枚举被模型写成了标题。它和真标题 `### 2.3.5 经典同步问题` 的区别**只在编号是否带点分层**。

另两条过滤：标题文字为空的不收（多是枚举残留）；标题超过 60 字的不收（多是被并进段落的正文）。

## 井号不可信，层级只认编号

实测同一份产物里 `2.3.5` 被写成 `###`、`2.3.6` 被写成 `##`——模型给井号很随意。

**层级按编号点数算**：`2.1` 一个点 → 2 级；`2.3.5` 两个点 → 3 级。**不要数井号**。

更强的验证：把整份产物里所有井号删掉，`buildOutline` 切分结果**一模一样**（44 节、4 个答案节，长度分毫不差）。因为 `buildOutline` 早就是按编号算层级。**所以"让转录模型管好标题层级"是伪需求**，改了也没用。

## 大纲必须排除枚举项

转录产物里有 `### 2．读者-写者问题`、`#### 1．生产者-消费者问题`——这是"1. 2. 3."枚举被模型写成了标题。真标题长这样：`### 2.3.5 经典同步问题`。

两者区别**只在编号是否带点分层**。判据（`extractOutlineEntries`）：

- 编号必须是 `\d+(\.\d+)+`（带点分层）、`第N章`、或 `一、` 题组标题
- 单个数字 + 顿号/句点（`2．` / `1.`）一律当枚举，不进大纲
- 标题文字为空、或超过 60 字的不进大纲（后者多是被并进段落的正文）

## 转录 prompt 的规则取舍

`CLEAN_VERSION 5` 的关键改动：**明确告诉模型"层级不必精确"**。

原因是下游按编号判断层级，井号深度无关紧要；但模型会为了"凑一个合理的层级"去猜，反而容易把枚举项也写成标题。放开深度约束、只要求"标题是独立一行、编号与原文一致"，误判明显减少。

同时必须保留一条硬约束：**不要把正文错认成标题，也不要把标题并进正文段落**。后者更危险——标题被并进段落，正文里完全看不出来，分节就少了一节。

## 产物校验：三道防线，堵三类静默失败

都在 `packages/core/src/ingest/vision-clean.ts`，且**单页路径与批量路径共用同一函数** —— 否则一旦走了合批，校验就被绕过，事故从「单页偶发」变成「整批静默」。

```ts
assertPageCoverage(markdown, page, native)   // 每页必过，不合格抛错 → 该页重跑
dedupeParagraphs(markdown)                   // 在 normalizeCleanOutput 里自动调用
collapseSymbolNoise(markdown)                // 同上
```

### 1. 相对覆盖率（`assertPageCoverage`）—— 最要紧的一道

事故原型：p207 原文 1348 字符，产物只有 **91 字符（7%）**，`finish_reason=stop`、HTTP 200，看着完全正常，就这么写进了缓存。内容是断在「逻辑地址结构为」的半个题干，下游会当成一页完整的题目。

判据是**相对比例**（产物 / 原文 < 0.35 判失败），不是绝对长度：

> 封面页 85 字符是正常的，正文页 91 字符就是失败。**只有同比能分开这两者。**

为什么是 0.35：清洗要去页眉页脚、合并断行，健康页实测多在 0.8~2.0（超过 1 是模型把代码/表格展开了）。少到只剩三成，就不是「简洁」，是漏了整段。

只在**原文 ≥ 300 字符**时套用比例判据：图片为主的页文本层可能只有几十字符，那种页产物比原文长很正常，拿比例卡会误杀。

同函数还挡两类：产物长度 < 60（模型基本没输出）、输出里含指令原文（模型把提示词抄回来了）。

### 2. 整段去重（`dedupeParagraphs`）

GLM 有个稳定的坏毛病：**把同一段正文输出两遍**。全书 358 页里 **49 页**中招，最严重的 p235 重复了 3705 字符（占该页三分之一）。整本书「缓存字符数 / PDF 原文」平均 159%，就是这个原因——不是转录得详细，是抄了两遍。

危害不是浪费字符，而是**下游按段落切题，同一段出现两次 → 同一道题被切出两道**。这种重复内容哈希不同，去重逻辑抓不到。

判定口径：
- 只删**长度 ≥ 40 字符**且归一化后完全相同的段落。短段落（选项 A/B/C/D、公式、小标题）**保留**——连着几行 `A.` 是正常的，删了会毁内容。
- 判重键用 `p.replace(/\s+/g, '')`，**完全去掉空白而不是压成单空格**。中文排版里「最核心的」和「最 核心 的」是同一句话；压成单空格会让两者判为不同，去重直接失效（实测踩过这个坑）。
- 保留**第一次出现的位置**，不是「保留最长的」。模型通常先写对后写重，保序能让页面结构和原书一致。
- `paras.length < 3` 直接返回——单段或两段的页面不需要去重。

### 3. 符号噪声（`collapseSymbolNoise`）

模型遇到流程图/表格时，偶尔不写占位符，而是用 `→` `|` `─` 硬画。实测 p305 一页产出 **2184 行纯 `→`**（占该页 98% 的行），9978 字符里只剩几百字有效内容。

处理：**连续 3 行以上**的纯符号行整块换成一行占位符 `⟦图表：原图为流程图/表格，此处无法逐字转录⟧`，保留「此处有图」的位置信息。零散符号行（表格边框、单个箭头）不动——那是有效内容的组成部分。

修复后 p305 从 9978 字降到 1266 字。

### 修复已有缓存，别急着重跑全书

上面三类问题里有两类**不需要重新调模型**：

- 重复段 → 纯文本处理，就地重写缓存文件
- 符号噪声 → 同上
- 内容缺失 → **修不了**，必须删掉缓存让它重跑

重跑全书 371 页要 2 小时且烧 token。能就地修的别重跑。修复脚本要**复用线上那套函数**（`dedupeParagraphs` / `assertPageCoverage`），避免「修复脚本认为没问题、实际流水线会拒绝」的错位。

## 合成全书与产物净化（实测踩过的坑）

## 合成全书：先确认「缓存真的命中」

用 `vision-clean.ts --pages 1-371 --out os.clean.md` 合成，正常情况下应当**清洗 0 次**。日志里的 `完成：371 页 / 清洗 N 次 / 缓存命中 M` 就是判据。

⚠️ **看到 `清洗 356 次` 就说明缓存没命中，立刻停**。实测这一次把全书重跑了一遍（3145 秒），期间 2 页返回坏结果覆盖了原本正常的缓存。

缓存命中要求**四个字段全部匹配**：`v === CLEAN_VERSION`、`file === 全文 sha256`（64 位，不是目录名的前 16 位）、`model`、`dpi`、`effort`。

### 版本号不一致时：先验证内容，再决定要不要重跑

盘上 269 页是 v7、102 页是 v8 时，直接跑会把 269 页全部重调模型（约 1.5 小时、110 万 token）。

正确的做法是**拿三条硬指标去验 v7 的内容**（覆盖率 >= 0.35、无整段重复、无符号噪声、长度 >= 60）。全部达标就说明内容可用，只需要把 `v` 改成当前值。

版本号只是「prompt 改过」的记号，**不构成「产物坏了」的理由**——真正该看的是产物本身。

⚠️ 但有个前提：如果新版本改的是**版面规则**（比如标题层级），旧产物可能结构不对，那种情况必须先读 diff 确认改了什么，不能这样搬。

## 覆盖率校验默认必须开启（踩过的坑）

`assertPageCoverage` 依赖 `native`（PDF 文本层）做基准。而 CLI 里 `withNativeText` 原先只由 `--with-native` 控制，**默认关闭** —— 于是这条校验在线上形同虚设。

实测后果：p227 产出 344 字符（原文 1363，仅 25%）、断在「磁盘I/」，日志照样报 `OK` 并写进缓存。

现在 CLI **默认提取文本层**（用 pymupdf 一次性导出，纯本地操作、不花钱）：

```ts
withNativeText: true,
nativeText: (page) => lenMap.get(page)
```

只回**长度**不回正文——校验只看 `native.trim().length`，传真实文本会把整本书的脏文本层（约 40 万字符）搬进内存，没有收益。用等长占位串（`'字'.repeat(len)`）表达即可。

提取要写临时文件而不是读 stdout：**MuPDF 会把 `MuPDF error: ...` 警告写进 stdout**，混进 JSON 直接解析失败。

## 归一化链：顺序很重要

`normalizeCleanOutput` 里的调用顺序是有讲究的：

```
stripSelfTalk（剥独白） → stripRunningHeaders（剥页眉） → dedupeParagraphs（去重） → collapseSymbolNoise（压噪）
```

**剥独白必须在去重之前**。模型「多遍重写」时会在每遍前面挂一串过程性独白（「现在检查是否符合规则：」「现在整合后的内容：」「这样处理后，符合所有规则：」），把重复的正文粘成互不相同的段落。不先剥掉，去重按整段比较时对不上，只能删掉很少一部分——实测 p52 一页被写了三遍，剥独白前几乎去不掉。

## 去重：保留终稿，不是草稿

模型写两遍时，**第一遍通常是草稿**（带自我说明、正文被截短），第二遍才是终稿。

所以 `dedupeParagraphs` 遇到重复 key 时**用后一份覆盖前一份**，而不是丢弃后一份。最初实现是「保留第一次出现」，结果 p50 留下残稿、删掉完整版，5440 字符被削到 2754。

保留原位置（不挪到末尾），只把该位置的文本换成更完整的那份，以免破坏「标题在前、正文在后」的结构。

长度阈值看**原始段落**（`p.trim().length`），不是去空白后的 key：中文段落去空格后常常刚好掉到 39，会把长段误判成短段落而跳过判重。

## 大纲：三个必须过滤的坑

`extractOutlineEntries` 从正文抽章节条目，踩过三个坑，都造成了「大纲页码整体错位」：

### 1. 目录页整页跳过（`looksLikeTocPage`）

目录页上的章节标题后面跟的是**书里的印刷页码**，不是我们的 PDF 页码。收进来会让几十条小节的页码全指向目录页自己。

最初靠「连续 `·` 连成 3 个以上」识别，抓到了 p7。但同一本书的 p9、p10、p11 整页也是目录、**没有点线**，只有堆叠的章节标题 —— 于是 3.1、3.2、第4章、4.1…… 几十条页码全标成了 9。

正确判据是**形态**而非点线：标题行占比 >= 60% 且**没有任何 >= 60 字的正文段落**。正文页正好相反——标题是少数，主体是成段文字。

### 2. 章标题必须独占一行

事故：前言页里有一句「…第 3 章内存管理、第 4 章文件管理…」，被当成章标题收进大纲，第 3 章标成了前言页的页码（实际在 p187）。

判据：真章标题长度有限（<= 24 字），正文引用会带逗号、顿号、句号或长长的说明。

### 3. 章名与章标题可能分两行

实测第 1 章首页排版是：

```
第 1 章
计算机系统概述
```

只认同行的话，第 1 章标题抽不出来，整章从大纲里缺失。所以「章号独占一行」时往下看**跳过空行**取标题（Markdown 里标题和正文之间必有空隔行，直接取下一行只会拿到 `''`）。

### 4. 大纲去重的键不能含页码

页眉残留会让同一章标题在 9~14 页重复出现。若去重键带 `page`，每页各留一条，大纲里出现十几个「第2章」。

键用「编号 + 标题」，**保留第一次出现的位置**——那才是这一章真正开始的地方。

## 页眉剥离：只认带页码的形式

`stripRunningHeaders` 只剥**页首/页尾 3 行内**且形态明确的：

- 带页码的章名页眉：`第2章 进程与线程 62`
- 孤立页码：`62` / `· 62 ·` / `第 62 页`
- 书名 + 页码

**绝不能只判「第N章 + 短标题」**。踩过：第 1 章首页那个大号标题「第 1 章 / 计算机系统概述」正好在页首，被当成页眉剥掉，整本书的第 1 章标题就此消失。

另外 **`isHeaderish` 对空行必须返回 `false`**。最初让它对空行返回 `true`（想顺带跳过排版空行），结果循环一路吃进正文——把第 1 章首页从 3420 字符削到 771 字符（丢了 78%）。
