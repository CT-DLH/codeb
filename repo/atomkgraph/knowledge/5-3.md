# 题库维护方案：5 个规模瓶颈与 3 级优先级策略

题库维护方案。权威源 `docs/12-题库维护方案.md`（62 行，5 个规模瓶颈 + 3 级优先级策略）。

## 一、当前题库的 5 个规模瓶颈

| # | 问题 | 现状 | 后果 |
|---|---|---|---|
| 1 | 只能单条录入 | `akg_create_question` 一次一题，无批量入口 | 50 题要 50 次调用，导入教材习题极低效 |
| 2 | 无去重 | 有 `content_hash` 字段和索引，但 create 时不校验 | 重复导入同一份资料会产生重复题 |
| 3 | 无分页 | `findAll()` 全量返回；`draw`/`wrong-set` 无上限 | 题目上千后列表接口变慢、前端卡 |
| 4 | 多对多用 LIKE 查询 | `findByKnowledge` 走 `LIKE '%"id"%'` 全表扫 | O(n) 扫描，题量上去后「按知识点查题」越来越慢 |
| 5 | 关联无校验 | `relate_knowledge_ids` 是 JSON 数组，指向已删知识点无人管 | 出现悬空关联，抽题时命中不到 |

## 二、维护策略（按优先级）

### 🔴 必做（题目上百前）

**1. 批量导入 + 结构化格式**
仿照知识点已有的 `akg_import_knowledge`，给题库也做一个批量入口。格式建议用 JSON（比 LLM 拆解更可控）：

```json
[
  {
    "content": "下列...",
    "type": "single",
    "options": ["A选项","B选项","C选项","D选项"],
    "answer": "B",
    "analysis": "...",
    "difficulty": 0.3,
    "relate_knowledge_ids": ["kn_xxx"],
    "diagnosis_hint": "选C说明混淆了...",
    "pitfall": "注意..."
  }
]
```

一次请求入库整批，返回 `{created, skipped, ids}`。

**2. 去重**
`create` 时用 `content_hash` 查重（字段和索引都已就位，只差逻辑），命中则跳过并计入 `skipped`。

**3. 分页**
列表/错题集/抽题都加 `limit` + `offset`（或游标），默认 20。

### 🟡 题量上千前

**4. 建关联表替代 JSON + LIKE**
新建 `question_knowledge (question_id, knowledge_id)` 多对多表，加双向索引。查询从「全表 LIKE」变成「走索引 JOIN」。这是**结构性改动**，要迁移现有数据。

**5. 软删除治理**
题目软删除后仍占表、仍可能被 LIKE 扫到。定期归档，或加 `review_status='rejected'` 与 `deleted_at` 的清理策略。

**6. 关联校验**
删除知识点时，清理指向它的 `relate_knowledge_ids`（类似刚做的子节点上提，属于「引用完整性」问题）。

### 🟢 长期

**7. 按维度检索**：题型/难度/来源/考点标签的过滤索引
**8. 题目版本历史**：仿 `knowledge_revision`，给题目也做快照

> 题库应该也和知识点库一样看齐，有些后续添加的知识点应该也能被之前的题目正确关联，也使用向量建立索引。
