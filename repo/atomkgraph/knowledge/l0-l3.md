# 内容录入流水线：L0 解析到 L3 落库的四层与静默失败

从一份文档（PDF/DOCX/飞书/Markdown）到题目+知识点落库的**产品级**录入链路。权威源 `docs/15-内容录入流水线.md`（33 章，每章对应一个需求 R36–R68）。四层结构：**L0 解析 → L1 切分 → L2 抽取 → L3 落库**，当前骨架是 **R42 统一录入**。知识点侧的查重/归并流水线另见 `knowledge/point-pipeline`。

## 四层流水线

- **L0 解析**（`packages/core/src/import/parsers`）：PDF（`pdftotext -table` 优先，空则 `pdftoppm`+OCR 兜底）、DOCX（解 zip 读 word/document.xml）、飞书（lark CLI）、Markdown（直接）。`--token` 绕过 LLM。解析结果缓存到 `.cache/import-cache/`（**缓存键含 L1/L2 prompt 版本号**——改切分或抽取 prompt 要 bump 版本，否则读到旧缓存）。
  - **扫描件另走视觉转录**：pdfjs 读 JPEG2000 页面图会崩（`JpxError: OpenJPEG failed to initialize`），但 pymupdf 能读出文本，很容易误判成"有文本层"。这类必须走 MuPDF 渲染 + 视觉模型，详见 `knowledge/pdf`。
- **L1 切分**（`splitMarkdownByHeading` → `splitIntoBlocks` → `mergeShortBlocks`）：先按标题分 section，再按**题号正则**切块，短块（≤120 字）归并进前块（**但要保护纯公式块**——LaTeX 环境不并入，否则 `\begin{cases}` 会被拆散）。
- **L2 抽取**（`buildUserPrompt` → `callExtract` → `extractJson`）：把块喂 LLM，返回结构化题目+知识点。这是最容易出「静默失败」的一层，见下。
- **L3 落库**（`packages/core/src/import/storage.ts`）：`placeInPaper`（卷内连续计数，不靠 part 固定跨度）、`questionOrder`（每 part 起 0x10000，题间步长 0x100）、`duplicateWithinPaper`（同卷去重）。**导入时只建 questions/knowledge，不填 paper/paper_part 表**——卷号信息全在 `import_batch.source_detail` 前缀里，L4 再落卷结构。

## R42 统一录入（当前骨架，5 步）

`/api/import/unified` → `planUnifiedIngest`（dry-run 出计划）→ 人审 → `plan_reviewed` → `applyUnifiedPlan` 落库。四类实体（知识点/题目/关系/学习资源）走同一套 plan，一次审阅一次应用。

## 录入环节的「静默失败」（最该记住的部分）

**LLM 幻觉不报错**：模型把某题抽漏了、或把「例题」当「练习题」，`JSON.parse` 照样成功——**静默失败，只有靠测试里的题目总数能看出**。所以验收**不写硬编码的全局总数**，而写「相对差值」（用真库跑之前先算实际数，再逐项断言差值）。

**字段静默缺失**：少一个 key 会静默用默认值（`question_type ?? 'single'`、`analysis ?? ''`），**不报错**。验收要显式断言关键 key 存在。

**`paper_part_id` 空**：LLM 漏抽某道题的 part → 题目静默落入未分配池。**不是 bug**（`placeInPaper` 故意这样降级），但导入后要人工核对 part 归属。

## 三个真机上才暴露的陷阱（改代码前先读）

1. **LaTeX 反斜杠会毁掉整个 JSON**（最隐蔽）。模型写 `\le` → JSON 里 `\l` 是非法转义 → 整批报废。更阴的是 `\frac` 的 `\f`、`\theta` 的 `\t`、`\rightarrow` 的 `\r` 都是**合法** JSON 转义，会被**静默**解析成换页/制表/回车控制字符——不报错，但公式已经被改掉了。修法：`llm/json-repair.ts` 的 `fixInvalidEscapes()`，字符串内只保留 `\\` `\"` `\/` `\uXXXX`，其余反斜杠加倍。
2. **同一行挤着多道题**。`line.match()` 非全局只拿第一个匹配，而 PDF 文本层常把 3、4 题并到一行。同理题号常被挤到**行中间**，只认行首会漏题。必须**全局**扫描。
3. **模型可用性是动态的**。同一个 key 昨天可用、今天直接 404「Not found for account」。**别把模型名写死在心里**，报 `LLM_REQUEST_FAILED` 404 时先换模型再怀疑代码。

## 导读块的坑

容器导读（`container_intro`，挂在容器上的引言）**不含题号**。若 L1 把导读和第一题切成同一块，L2 会把导读**整段塞进第一题的题干**——**静默**。修法：`splitContainerIntro()` 把纯导读段与含题号块分开。

## 切分只认编号，井号不可信（buildOutline 的真实行为）

`packages/core/src/ingest/outline.ts` 的 `buildOutline` **按标题编号算层级**（`label.split('.').length - 1`），不数井号。

验证方式很直接：把整份清洗产物里所有 `^#{1,6}\s+` 删掉再跑 `buildOutline`，切出的节数、每个答案节的正文长度**分毫不差**（实测 44 节 / 4 个答案节）。

**推论（重要）**：让视觉转录模型"把标题层级写准"是**伪需求**。模型给井号很随意——实测同一份产物里 `2.3.5` 写成 `###`、`2.3.6` 写成 `##`。下游根本不吃这个，改 prompt 去约束它只是在治不存在的病。

**但有一条必须以编号为准的陷阱**：`h.level > maxLevel` 会丢弃深层小节。某本教材的 `2.1.10 答案与解析` 作为二级标题被保留，而它前面有大量三级小节（`2.1.1`~`2.1.9`）被 `maxLevel: 2` 丢掉——于是答案节把后面所有内容都吞进自己，直到下一个二级标题。表面上"答案串到下一节去了"，实际是**切分层级过滤吃掉了小节的边界**。

**遇到"答案错配到下一节"时，先查这一节的边界是不是被吞了**，别急着怀疑配对逻辑。

## 跑完整本书后必查的三项

流水线报「全部成功」不等于结果可用。这三项是实测中真实翻车过的地方，缺一项查都可能把缺陷带进知识库。

### 1. 缺页 —— 缓存页数 vs PDF 页数

缓存目录 `.cache/vision-clean/<sha前16位>/p%04d.json`。**并发跑久了会漏尾页**：实测跑到 p358 就停了，而 PDF 有 371 页，13 页从未转录。日志末尾是正常结束，看不出异常。

判据：缓存页号集合 == `1..pdf.page_count`。

### 2. 覆盖率 —— 每页产物长度 / PDF 文本层长度

`assertPageCoverage` 已内建（< 0.35 判失败），但**对历史缓存要单独审计一遍**——校验是后加的，旧缓存没经过它。

```python
# 拿 pymupdf 一次性导出每页文本层长度，别 371 次起进程
import pymupdf, json
doc = pymupdf.open(pdf)
with open('.tmp_native_len.json','w',encoding='utf-8') as f:
    json.dump({i+1: len(doc[i].get_text().strip()) for i in range(doc.page_count)}, f)
```

⚠️ 走临时文件而不是 stdout：**MuPDF 会把 `MuPDF error: ...` 警告写进 stdout**，混进 JSON 里直接解析失败。

比阈值更该记住的是「看结尾」：断在半句的页，最后一句通常是一个不完整的短语（「断在『逻辑地址结构为』」）。比数字更直观。

### 3. 重复与噪声 —— 纯文本就能查，不必重跑模型

- **整段重复**：按 `\n\n` 切段，长度 > 120 的段落若出现重复计数。实测 49/358 页中招。
- **符号噪声**：整行只由 `→←↑↓|│─┌┐└┘├┤┬┴┼` 组成的行超过 20 行。实测 p305 有 2184 行。

这两类**能就地修**（改写缓存 JSON），不要重跑——重跑 371 页要 2 小时且烧 token。**只有内容缺失必须重跑。**

修复脚本要复用线上那套函数（`dedupeParagraphs` / `collapseSymbolNoise`），否则会出现「修复脚本认为修好了、实际流水线仍会拒绝」的错位。

### 顺带一条：批量调用的 token 预算陷阱

批量预算 `maxTokens × 页数` 在智谱上必然撞顶：`2 × 8192 = 16384` 刚好是硬上限，3 页就 400（`max_tokens参数非法：限制数值范围[1,16384]`）。

表现出来只是日志里一行 `zhipu 400`，然后静默回退单页——**极难定位**。现在按 provider 封顶，且页数超出预算能装下的量就直接走单页，不发注定失败的请求。

## 扫描件与视觉转录的分工

`knowledge/pdf` 记的是视觉转录的完整实践（模型选型、多 key、三道校验、大纲）。这里只留一句接口说明：

- **pdfjs 崩 `JpxError` 而 pymupdf 能读文本** → 是扫描件（页面是整张 JPEG2000 图），必须走 MuPDF 渲染 + 视觉模型
- 视觉转录的产物落到 `.cache/vision-clean/<sha前16位>/`，之后才进 L1 切分
