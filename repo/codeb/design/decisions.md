# codeb: design decisions

记录「为什么是这样，而不是那样」。代码只能看到结果，看不到被否掉的方案——
所以这一页的重点是那些**当初看起来更好、实际被推翻**的选择。

## Rejected: fixed layers with a manifest

最初的方案是「灵活分层 + 知识归属 + Miss 闭环」：页面分成 entry / evidence 等固定层，
用 `manifest.toml` 集中登记所有页面，强制每页写 `## TL;DR`，并配 parent/children 关系，
再加三项目动化检查（漂移、覆盖、孤儿）。

**被否掉的理由**：把层数写死，小仓库会背负不必要的结构，大仓库又会被层数限制住。
而且 manifest 是最脆弱的一环——它一定会与目录树漂移，而漂移**不报错**，
后果是「查不到」与「没写过」无法区分。

现在的做法：**层数不写死，结构只有一个强制项（第一级目录 = 仓库）**，
索引就是目录树本身，`covers` 就是反向映射，两者都是现场算出来的。

## Rejected: automated lint

曾经设计过 `kb lint` 检查漂移、覆盖、孤儿页面。现在是明确不做。

完整的推理链有三步，缺一步这个决定就站不住：

**第一步，检查要求元数据同步维护。** 漂移检测必须知道「这页本该覆盖哪些文件」，
覆盖率统计必须知道「哪些文件该有页」——这些都得额外记账。
于是 LLM 每次写入都多背一份账本，而账本本身就会漂移。

**第二步，检查会改变写页的目的。** 一旦有检查，写页的人（或模型）会开始填那些
「为了过检查」的字段，而不是「为了表达知识」的内容。检查通过成了目标本身，
而检查通过与知识有用是两件事。

**第三步，检查的替代品是存在的。** LLM 自己读代码就能发现过时，人工 review 也会发现。
把防腐交给检查和交给维护者，前者成本高且会误报，后者更简单。

所以这一版选后者。如果将来要加，硬约束是：**独立的只读命令，绝不参与写入路径，
绝不要求额外元数据文件**——这三条一起才保证它不会退化成第二本账。

如果将来要加，硬约束是：独立的只读命令，绝不参与写入路径，绝不要求额外元数据文件。

## Rejected: embeddings for dedup

`kb search` 是逐行子串匹配，不是语义检索。

理由：这个库的规模（几十到几百页）下，子串匹配足够；而 embedding 引入两样东西——
模型依赖和索引文件——前者让工具不能「只用标准库」，后者正是上一版被否掉的 manifest 同构物。

代价是**同义词查不到**：搜「写入」找不到标题为 `Write channels` 的页。
缓解办法是 `covers` 与目录结构承担了大部分定位工作，而不是靠搜索措辞碰运气。

## Decision: search ignores whitespace

搜「软404」原本 0 结果，因为正文写的是「软 404」。

中英混排时有没有空格完全看作者习惯，而作者（模型或人）不会记得自己当初写的哪一种。
所以查询词与每一行**都去掉全部空白**再比。这条改动很小，但它决定了搜索能不能信任。

## Decision: never guess on ambiguity

`kb read l1-primitives` 若指向多页，工具**不选第一个**，而是列出全部候选并退出 2。

静默选错页是最坏的失败方式：调用方拿到了内容、以为拿到了正确的，实际是另一个仓库的同名页。
它不会报错，只会让之后的判断建立在错误前提上。

## Decision: English titles, Chinese body

标题英文是为了导航成本（见 `codeb/overview` 的「四条强制规则」）。
但**文件名也用英文**是另一个独立决定：文件名会出现在 `covers`、git diff、
shell 命令与 MCP 参数里，中文名在每一处都触发编码问题，而每次都要花时间确认「是显示问题还是真坏了」。

`repo/_shared/` 用下划线前缀而不是 `通用/`，同理：保留名用 ASCII，且 `_` 开头天然排在前面、
并被「跳过隐藏目录」的通用惯例保护。

## Decision: idempotent filenames

标题没有 ASCII 字符时，文件名回退到**标题的 sha1 前 10 位**（`page-<hash>`），
而不是时间戳或序号。

理由：同一个标题必须永远映射到同一个文件名。用时间戳或序号，
重跑一次同样的 `kb upsert` 就会多建一页，而「多出来的副本」在知识库里极难被发现和清理。

## Decision: one write entry point

`kb_upsert` 是唯一写入口，`kb_read` / `tree` / `heads` / `search` / `where` 全部只读。

这不是洁癖：第二个写入口意味着第二套关于 frontmatter 顺序、小节合并方式、
幂等规则、编码规范的处理。两套规则一定会在某个边界上不一致，而那个边界上的写入会静默出错。

## Decision: zero-dependency MCP

不引 `@modelcontextprotocol/sdk`，手写 stdio JSON-RPC（约 120 行）。

理由：这个 server 的全部工作是调一个 Python 脚本。SDK 会带来依赖树，
以及一整类「哪个版本改了分帧方式」的问题——而这类问题的表现是「客户端连不上」，
排查时很难想到是 SDK 版本。

代价明确：将来要用 resources / prompts / sampling 得自己加。这个代价被接受，
因为这个 server 只需要 tools。

## Decision: Node 24 runs .ts directly

没有构建步骤、没有 `dist/`、没有 watch 进程。

代价写进 README：**降级到 Node 22 及以下就失效**。
这是一个明确的、单一版本的赌注，换掉了「构建产物与源码不同步」这一整类问题。

## What I would change if the library grows to thousands of pages

现在全扫是毫秒级，所以「无索引」是净收益。到上千页时它会变成瓶颈，届时需要：

1. 仍然不引入 manifest，而是引入**可丢弃的缓存**（删掉不影响正确性，只影响速度）；
2. 缓存必须能从目录树完整重建，否则它就变成了第二个真源；
3. `covers` 需要建反向映射，因为它是全扫里最贵的部分。

第 2 条是底线：**缓存可以错，但不能成为真源。**

## Side by side with the rejected version

| 维度 | 被否掉的版本 | 现在 |
| :-- | :-- | :-- |
| 层级 | 固定 entry/evidence + 项目声明中间层 | 只有「第一级目录 = 仓库」一层强制；往下按源码路径折叠 |
| 元数据 | `manifest.toml` 集中登记所有页面 | 只在页面内写可选的 `covers` |
| 页面格式 | 强制 `## TL;DR` + parent/children/impl | 只要有一个标题；标题英文、正文中文 |
| 索引 | manifest 里的 children 树 | 目录树本身，现场扫 |
| 防腐 | 漂移 / 覆盖 / 孤儿三项检查 | 无，交给维护者与 review |
| 遗漏处理 | `kb.capture` + reusable 分流 | `kb where` 查、`kb upsert` 补 |
| 写入接口 | 无 | MCP + CLI，共用 `kb.py` |
| 代码量 | 核心 + 检查 + 符号索引 + MCP | 单个 `kb.py` + 一个薄 MCP 壳 |

这张表的价值不在「现在更好」，而在**记录被否掉的具体形态**。
否则过一段时间，会有人（或模型）重新提出「加个 manifest 集中管理页面」，
而这个提案听起来很合理——直到有人指出它已经被试过、以及为什么失败。
