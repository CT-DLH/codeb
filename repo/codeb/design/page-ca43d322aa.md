# Capture loop: who writes, and when

知识收割环节的 actor / trigger 分工，以及为什么不能指望在场 agent 自觉回写。
这条推理来自真实观察：在场 agent（包括设计这套机制的那次会话）不会主动写入。

## 在场 agent 不回写是结构问题，不是态度问题

三件事同时成立，所以它必然不发生，加任何指令措辞都没用：

1. **收益落在未来的另一个 agent 身上。** 写入对当前任务零回报，只有成本。
   我的回合由"当前任务做完"评价，不由"库变好了"评价。
2. **指令没有触发时刻。** 「收工前记得 upsert」里的"收工"对 agent 不可观测——
   回合不是结束在某事件上，是结束在我没有更多话要说上。
   没有可观测触发点的指令是愿望，不是机制。
3. **真正的成本是"生成候选"，不是"执行写入"。** `kb_upsert` 已经很便宜了。
   但先要意识到"这条值得写"，而这个意识不会在干活时自己冒出来。

判据：**agent 对"批准眼前现成的东西"高度可靠，对"主动发起生成任务"高度不可靠。**
所以任何要求 agent 自觉写入的设计都失败；把写入变成一次批准才会成功。

## 长会话里在场回写根本不可能（决定性理由）

上下文折叠会把材料彻底销毁：`task_end` 之后只有结论存活，中间步骤被折掉；
assistant 消息一多，更早的探索也会从窗口里消失。

于是最该被记录的东西——**当时考虑过又被否掉的方案**——恰恰是
在场 agent 到回合末期已经不再持有、而后台蒸馏器永远读不到（它没进日志）的那部分。
这条决定了 P1 的采集必须在**发现的那一刻**，而不是"收工的时候"。

## 分工：按知识类型切，不按能力切

| 知识 | 由谁 | 为什么只有它能做 |
| :-- | :-- | :-- |
| S1 刚付费的探索、S3 死路、S6 与页面矛盾 | 在场 agent，发现即触发 | 只有它知道哪些文件烧掉了调用、预期与实际差在哪。"我差点走这条路"从没进过日志，后台无法恢复 |
| 跨会话的整体理解、长会话补档 | 后台蒸馏器 | 在场 agent 已经没有材料了 |
| 是否值得写（DESIGN 三条件） | 闸门 + `bar` 必填 | 判断标准可以每次现读 DESIGN.md，不必留在记忆里 |

后台 LLM 的合规率是它的唯一优势，也是它的全部优势：它没有别的事 competing，
写入就是它整个任务。它不能取代在场采集，只能当兜底。

## 让在场 agent 写入的唯一可靠机制：审批而非创作

触发时刻由插件观测（`turn/end`、S1 计数达标），不是由 agent 记忆。
届时 `agent.inject()` 送进去的**不是一句提醒**，而是一条填好参数的 `kb_upsert` 调用：
标题从它刚读的文件猜、`covers` 就是它刚付过费的路径、`topic` 由目录推、
`section` 从 `kb_heads` 现取。agent 只改一个字符串，或者回一句"不要"。

这把作者成本（几百 token 的判断）换成批准成本（一次调用）。
`agent.inject` 而不是 `agent.followup`：不唤醒、不打断当前任务，
材料在 inbox 里等，下一个自然输入到达时才出现。

## 后台蒸馏器的强制约束（否则它比不写更糟）

- 只出**候选**，落盘仍走 `kb_upsert` 这个唯一写入口，绝不直接改 md。
- schema 里 `rejected_alternative` 必填。摘要器最典型的退化是把
  "在 A 和 B 之间选了 A，因为 B 会撞上 X" 压成 "选了 A"——被否掉的形态正是唯一值钱的部分
  （见 `codeb/design/decisions` 那张 side-by-side 表存在的理由）。
- 噪音页比缺页更糟：读者不知道信哪个，之后没人会去合并。
  所以宁缺毋滥是硬门槛，不是风格偏好。
- 多会话并发写会互相覆盖（`codeb/overview` 明确无写保护），
  **自动化开跑前必须先给 `upsert` 加锁**，否则只是放大静默丢失。
