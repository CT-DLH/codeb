# Where knowledge belongs

代码里该写什么注释、什么该进知识库，只用一个问题判断：

> **改动这行代码时，是否必须同步改动这条说明？**
> 是 → 留在代码里。否 → 进知识库。

这个判据之所以是一个问题而不是一张清单，是因为清单永远列不全，而问题可以现场回答。

## The split that follows

| 知识类型 | 放哪 | 理由 |
| :-- | :-- | :-- |
| 模块职责、设计意图 | 知识库 | 跨文件，需要全局视角 |
| 历史决策（为何选 A 不选 B） | 知识库 | 代码里写不下完整背景 |
| 函数级约束（非空、范围、调用顺序） | **代码注释** | IDE 可见，与实现行绑定 |
| 复杂算法步骤 | **代码注释** | 改算法必须同步改，放库外容易脱节 |
| 已知 bug 的复现条件 | 知识库（排查记录页） | 需要上下文，且允许长期保留 |
| 使用示例、教程 | 知识库 | 示例会污染代码上下文 |

## Why this line, and not another

判据的实质是**过期成本落在谁身上**。

留在代码里的注释只剩两类：**约束性**（「不能传 null」）和**局部实现说明**（「此处二分因数组已有序」）。
它们的共同特征是：短、与行绑定、**过期了会被编译器或测试抓到**。

而知识库里的内容过期了不会被抓到——没有编译器检查「这段历史决策还成不成立」。
所以知识库只放**过期了也不致命**的东西：设计意图、历史背景、已知问题的复现条件。
这类内容的半衰期长，且即使部分失效，仍然提供「当初为什么这样想」的价值。

反过来，把约束性注释搬进知识库是明确的坏做法：
改代码的人不会去翻知识库，于是最需要被看到的那句话恰好没人看到。

## The failure mode this prevents

最典型的错误是把两者混在一起，然后各自都做不好：

- 代码注释里写大段设计背景 → 三个月后没人敢删，也没人读，逐渐变成谎言。
- 知识库里抄一遍函数签名和参数说明 → 代码一改就过时，而且没人会去同步。

第一种的代价是注释失去可信度，第二种的代价是知识库失去可信度。
**可信度一旦失去，整个机制就退化成「没人看的东西」**——这比没有更糟，因为它占用了维护成本却没有产出。
