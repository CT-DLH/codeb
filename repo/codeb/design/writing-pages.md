# How to write a page that is worth reading

结构自由——没有必需段落、没有固定小节名、没有 TL;DR 契约。
但自由不等于随便写，下面五条是**实践建议，工具不检查**，它们决定这一页三个月后还有没有人读。

## Lead with the conclusion

第一个标题下面先说**这页能回答什么问题**，不要开头先铺垫背景。

判断方法：把首段单独拿出来读，如果读完还不知道这页要讲什么，它就没起作用。

## One page, one topic

超过两屏就拆。拆的依据是「**会不会被一起需要**」，不是「代码是不是一个文件」。

这两个依据经常给出不同答案，此时以「会不会被一起需要」为准：

- 采集模块的翻页、限速、抽正文三条规则分散在三个文件里，但改抓取逻辑时通常要一起看 → 合成一页。
- `kb.py` 与 `mcp/server.ts` 是两个文件，但「规则只有一份实现」这条约束横跨两者 → 合成一页。

反过来，`covers` 与 `tree` 都在 `kb.py` 里，但一个用于上行反查、一个用于下行导航，
使用者很少同时需要 → 分两页。

## Write why, not what

「这里用 `!=` 而不是两个分支，是为了让取反严格等于补集」——**有价值**。
「这个函数接受两个参数」——**没价值，代码里有**。

这条规则的实际检验：如果一段话在代码改坏时**不需要改**，它大概就是有价值的知识；
如果代码一改它就得跟着改，那它本来就该在代码里（见 `codeb/where-knowledge-goes`）。

## Record the known problems

这是知识库相对代码**最大的增量**：代码只表达现状，不表达「哪里将就了」。

代码不会说「这里按状态码判断翻页是错的，但历史上就是这么写的」，
也不会说「这个缓存 key 里放 system prompt 是因为有一次改 prompt 忘了 bump 版本」。
这些信息只存在于人的记忆里，而记忆会随着会话结束而消失。

写下来之后，接手的人（或下一个会话的模型）就不会把「将就」当成「正确」去扩展。

## Make the heading an intention

`## Why no mmap` 比 `## 实现细节` 有用，因为**前者本身携带信息**。

这条在 `kb heads` 的语境下尤其重要：`kb heads` 会列出一页的全部标题，
如果标题都是「概述」「细节」「其他」，那这个列表就没有导航价值，
调用方只能整页读——`--section` 的意义也就没了。

标题写成意图，等于让页面**自己充当索引**，而这是 `--section` 能省下 87% token 的前提。

## The meta rule

一页写得好不好，有一个便宜的检验：**看它的 `kb tree` 提示行能不能让人决定「要不要点进去」**。

那行是正文首句（`kb tree` 自动截取）。如果首句是「本文介绍……」这种空话，
提示行就浪费了；如果首句是「翻页只按新增条目数判定，因为软 404 会返回 200」，
读的人立刻知道这页是不是自己要找的。

提示行不是单独写的，它是首句的副产品——所以这条检验实际上是在要求：**首句就要有信息量**。
